# 보안 / 안전성 가이드

## 위협 모델
- AI가 파괴적 셸 명령 실행.
- 외부 플러그인이 프로젝트 경계를 벗어나 삭제.
- 심볼릭 링크 / junction 경유 디렉터리 탈출.
- Docker socket 직접 접근으로 프록시 우회.
- GC 계획 후 파일이 변경되는 TOCTOU.
- 멀티 에이전트가 서로의 활성 빌드·테스트 리소스를 삭제.

## 원칙
1. 기본은 read-only + dry-run.
2. 영속 볼륨, 프로젝트 소스, 사용자 자료는 자동 GC 금지.
3. 프로젝트 설정은 시스템 안전 정책을 완화할 수 없다.
4. Docker socket 직접 접근이 가능하면 `enforce`가 성립하지 않는다.
5. PID만 믿지 말고 프로세스 시작 시각과 lease 검사.
6. 재생성 가능한 캐시라도 공유 사용 여부 확인.
7. `gc apply`는 계획을 재검증하고 별도 승인 필요.
8. 플러그인은 별도 프로세스와 최소권한 적용.

## Docker 조회 브로커의 경계

브로커는 Unix 피어 자격 증명으로 연결 사용자를 판별하고 변경 요청을 엔진에 전달하지 않는다. 엔진을 Unix 소켓 경로와 ID에 고정하고 필드가 정해진 조회를 수행한다. 운영상 강제 통제는 서비스 계정 외 접근을 거절하는 엔진 구성과 대상 플랫폼의 별도 계정 검증을 전제로 한다. 동일 UID의 프로세스는 운영상 같은 신뢰 주체로 다룬다. [설정 및 검증](OPERATIONS.md#docker-조회-브로커)

Linux ARM64의 로컬 제어 서비스 프로브는 root 소유의 전용 소켓, 예상 피어 PID와 프로세스 세대, 읽기 전용 프로토콜 선언을 확인한다. 호스트 root는 이 검증의 신뢰 경계 안에 있다. 운영 적용을 열려면 권한 제어기의 배포 출처, 서로 구분된 승인·실행 주체, 프로젝트와 자원의 소유권을 결합하는 보호된 기록부, 다른 변경 경로를 차단한 전용 엔진이 필요하다. 검증 응답은 전용 서비스가 밝힌 선언이며 적용 게이트는 `preserve_unverified_control`을 유지한다. [프로브 계약](API_SPEC.md#로컬-docker-제어-서비스-읽기-확인)

Linux ARM64 코어는 쓰기 요청의 연결 피어와 메시지별 커널 자격, 송신 pidfd를 각각 대조한다. 소켓 FD를 넘겨받은 다른 프로세스는 연결 생성자의 역할을 사용할 수 없다. 승인 전용 요청과 실행·복구 요청을 구분한다. 코어 어댑터는 root가 통제하는 등록부의 SQLite 배타 슬롯에서 보호 정책과 엔진·역할 세대, 자원 범위를 승인·적용 의도에 결합한다. 실제 배포는 설정 교체 뒤에도 동일 보호 등록부와 안정적인 엔진 자원 범위를 유지해야 한다. [요청 계약](API_SPEC.md#보호된-docker-제어기-배포-확인)

보호된 배포 정책을 사용하는 Linux ARM64 제어기 확인은 제어기·엔진의 root 피어와 서로 다른 비root 승인자·실행자의 소켓을 구분한다. 부팅 ID, pidfd, 시작 시각, 실행 파일과 SHA-256을 대조해 현재 세대에 대한 읽기 근거를 기록한다. 보호된 Unix 소켓 확인의 범위는 관측한 네 로컬 피어다. 운영 쓰기 연결에는 배포물 출처의 신뢰, 프로젝트별 출처와 소유권, 요청별 승인 및 모든 변경 경로의 배타 제어가 필요하다. [배포 확인 계약](API_SPEC.md#보호된-docker-제어기-배포-확인)

별도 BuildKit의 합성 캐시 출처 확인은 전용 단일 워커와 정확한 ID의 읽기 대조로 제한한다. v0.35.1 공개 제어 API는 캐시 회수에 `Prune`만 제공한다. 이 요청은 이미지 캐시 lease, 워커 GC, 솔버 메타데이터에도 영향을 줄 수 있다. 단일 ID 회수에는 프로젝트 소유권과 참조의 직전 확인, 대상 변경, 영속 영수증 기록을 같은 배타 잠금으로 보호하는 경로와 대상별 승인이 필요하다. 현재 제품은 회수 후보 0개와 보존 판정을 유지한다. [공개 제어 API](https://github.com/moby/buildkit/blob/v0.35.1/api/services/control/control.proto#L12-L32) · [제어기 소스](https://github.com/moby/buildkit/blob/v0.35.1/control/control.go#L228-L266) · [워커 캐시 관리자 소스](https://github.com/moby/buildkit/blob/v0.35.1/cache/manager.go#L1018-L1042)

에이전트 훅 실패 시 차단 여부는 CLI의 동작에 따른다. macOS에서 Docker 직접 접근을 통제하는 수용 기준은 샌드박스와 검증된 서비스 경계로 적용한다. Windows의 경우 SCM이 소유한 named pipe에서 허용 SID를 검증한다. [에이전트 운영](OPERATIONS.md#에이전트-연동-운영)

## Python POC 경고
두 번째 환경변수 확인이 있지만 OS 전역 강제·활성 파일 잠금·안전한 경합 대응을 보장하지 않습니다. 실사용자의 프로젝트에서 `gc-apply` 실행을 권장하지 않습니다. POC의 Hook는 정규식 예제로 우회 가능합니다. 안전한 강제 구현으로 취급하지 마십시오.
